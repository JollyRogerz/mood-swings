# Game, UX and security review — 21 September 2026

Reviewed the updated application at `804cace` and its changes since the previous rules/UI pass. This review preserves the current visual design and existing gameplay. It concentrates on reproducible defects and the boundaries introduced by profiles, passkeys, voice, spectators, timers and substitute bots.

## How the game now fits together

- **Rules:** a deterministic TypeScript engine owns cards, prompts, turns and scoring. Planned choices and bot actions use that engine. The core engine is unchanged since the earlier rules audit; the newer clock, pacing and seat modules surround it.
- **Multiplayer:** a Colyseus room serializes mutations, saves the resulting snapshot, then sends a player-specific view. Players use a device token; spectators receive a public view without hands or private choices.
- **Persistence:** PostgreSQL in configured deployments, atomic JSON-file replacement locally. The saved game is authoritative; public room listings and voice presence are in memory.
- **Accounts:** optional Better Auth sessions, passkeys and configured social providers. Profiles associate device identities with an account. This is currently a profile/sign-in feature, not a persistent statistics or cross-device seat-recovery system.
- **Voice:** opt-in browser-to-browser WebRTC, with signaling through the table. Public STUN and optionally configured TURN help connections. Microphones start muted.
- **Client:** React provides card inspection, pre-play choices, reveals, score explanations, guided practice, spectators, sharing and mobile layouts. Optional preferences cover motion, audio, notifications and colour cues.

## Fixed in this pass

| Area | Defect or gap | Change and verification |
| --- | --- | --- |
| Scoring timers | The clock stopped whenever scoring began, including when a human still owed a scoring decision. A round could stall despite an enabled timer. | A pending prompt takes precedence over the scoring flag. Regression covers an Apathy scoring choice through overtime, automatic resolution and the next round. |
| Rematches | A temporary substitute bot lost its substitute marker when copied into a rematch. Its human could no longer reclaim it. | Rematch creation preserves temporary ownership, restores connected humans and leaves ordinary bots unchanged. Host authorization remains required. |
| Microphone privacy | Leaving while the permission dialog was open did not cancel the pending join. Granting permission later could capture audio after leaving the table. | Join attempts are invalidated on departure; late streams are stopped. Audio-context failures are caught. Browser regression leaves the table before granting permission and checks that tracks end. |
| Voice resources | Closing a peer left its audio-context listener and panner attached. | Peer teardown disconnects the audio graph and removes the listener, including when replacing a track. |
| Notifications | Rejected permission requests and unsupported `Notification` constructors could throw into the UI. Scoring prompts also missed turn notifications. | Permission failure leaves the preference off; constructor failure is contained; scoring choices qualify for notifications. Browser regressions cover rejected permission and a throwing constructor during an active two-player game. |
| Profile writes | Custom Express profile routes were outside Better Auth's own origin checks. | State-changing requests require an allowed origin and reject cross-site fetch metadata. Authenticated cross-site writes are regression-tested. Hosted deployments no longer trust localhost development origins. |
| Session signing | Memory mode used a publicly known fallback signing secret. | An unconfigured memory instance gets a cryptographically random process-local secret. Production PostgreSQL mode still requires its configured persistent secret. |
| Socket pressure | Some commands and sync requests bypassed limits; other limits ran only after requests had entered the serialized queue. | Limit client commands before enqueueing and bound sync responses. A real-socket test floods both paths, then verifies normal operation resumes. |
| HTTP errors | Room endpoints could send unexpected database or infrastructure error messages to clients. | Expected validation errors retain useful messages/statuses. Unexpected errors are logged server-side and return generic retry guidance. |
| Browser hardening | Responses lacked baseline framing, MIME and referrer restrictions. | Add anti-framing, `nosniff`, referrer policy and a limited CSP for framing, objects and base URLs. Profile responses are non-cacheable. This is not a complete script CSP. |
| Profile feedback | The profile screen claimed game history was saved when that feature was absent. Sign-out responses were not checked for returned errors. | Copy now describes what is actually saved; failed sign-out is handled as an error. Voice roster copy says “in voice” instead of claiming muted players are talking. |

## Prioritized improvements

### Next: trust and operational reliability

1. **Exercise production storage in CI.** Current server/account regressions use isolated files and memory accounts. Add a PostgreSQL service and cover schema initialization, simultaneous username claims, game restore, deletion failures and migrations. Add transactional account deletion so a failure cannot leave half-deleted profile/device records.
2. **Make account availability explicit.** The client can fall back to a guest presentation after a profile request fails. Distinguish “signed out” from “profile service unavailable”, offer Retry, and retain the local seat during an outage. Account startup failure should trigger an operational alert while games remain available.
3. **Separate liveness from readiness.** `/api/health` currently confirms the process is running. Add a bounded storage readiness probe, error monitoring and alerts for failed saves/reconnect spikes. Run a backup restore exercise and document rollback compatibility for saved snapshots.
4. **Implement real retention.** PostgreSQL stops loading games older than 30 days but does not delete those rows. File storage has no equivalent expiry. Add scheduled cleanup with documented retention and tests; never remove active games. Publish a short explanation of stored profile/device/game data and voice handling.
5. **Use short-lived TURN credentials before wider voice adoption.** Configured static credentials must reach seated browsers. They are unsuitable as a long-term abuse boundary for a paid relay. Add expiring credentials, usage caps and relay monitoring. Also offer a clear connection retry and voice troubleshooting state.
6. **Keep scaling deliberate.** The room registry, presence and request budgets are process-local. Do not assume adding Railway replicas will work without shared matchmaking/presence, room routing and distributed rate limits. Load-test active games plus spectators first.

### UI and interaction polish

1. **Keep one obvious next action.** Retain the current card art, score prominence and identity. During a turn, prioritize the playable hand, current decision and action button; move occasional controls into one consistent secondary menu. Desktop empty mood zones occupy substantial space before cards enter play; consider a compact opening layout that expands with the board.
2. **Improve mobile table awareness.** The existing opponent score/turn strip is useful; explore keeping it visible while the player works in their hand or a target panel. Make off-screen targets discoverable without requiring a search through the board. Preserve selection and the target budget while inspecting a card.
3. **Explain disabled and waiting states.** Use brief reasons such as “Reading Ember’s card”, “Waiting for a choice” or “Reconnecting”, with a visible countdown where one exists. Avoid unexplained disabled generic actions. Existing automatic reveal/results deadlines should remain; do not introduce a compulsory readiness gate.
4. **Make failures recoverable in place.** Keep the selected card/targets on retryable network failures. Give copying, sharing, notification denial and microphone denial distinct feedback and a next action. The notification safety fix prevents errors, but a denied permission still deserves clearer explanatory copy.
5. **Finish accessibility verification.** Existing touch tests cover narrow layouts, nested dialogs, focus restoration and card readability. Add automated accessibility checks plus manual keyboard and screen-reader sessions, contrast measurements, 200% zoom and real iOS/Android testing. Avoid announcing every card animation; announce the meaningful resulting state.
6. **Explain unmet score conditions.** The score dialog shows the correct total alongside conditional card text, but a player can see “12 if…” next to an actual value of 4. State the missing requirement directly (for example, which colour is absent for Love) and distinguish the active value from the possible value.
7. **Test voice comprehension.** Show “muted”, “connecting”, “connected” and “network blocked” distinctly. Let each listener adjust a peer's volume; consider a mono option alongside positional audio. Keep voice optional and muted on entry.

### Performance and architecture

- **Split optional client code.** The current production entry is approximately **662 KB minified / 182 KB gzip** and triggers Vite's size warning. Profile/auth, voice, catalog and advanced panels are candidates for lazy loading. Measure initial load and interaction latency on a throttled mid-range phone before/after; do not simply raise the warning threshold.
- **Profile crowded games.** Measure React rendering, card image decoding, snapshot size and server event-loop delay with four players and many spectators. Cache appropriately sized card thumbnails; load inspection-sized images when needed. Preserve legibility and avoid speculative virtualization before measurement.
- **Reduce change risk.** Extract connection/session lifecycle and major table panels from the large main component. Consolidate overlapping responsive CSS into clear component rules and shared spacing/typography tokens. Keep the established visual style.
- **Expand adversarial tests.** Add state-machine/property tests for disconnects during prompts, restarts during scoring, substitute/reclaim/rematch sequences and stale planned choices. Include network delay and packet-loss scenarios. Retain deterministic seeds in failures without storing private hands in public telemetry.
- **Treat bot strength as measurable.** The fly-brain bot is already integrated. Benchmark each difficulty against fixed opponents and seeds, measuring legality, win rate and decision time. Keep long bot computations from delaying unrelated rooms if profiling shows event-loop contention.

### Product and community

- Complete persistent match history before suggesting that profiles save results. Define whether history is per account or per device and how guest games are claimed.
- Before opening the public lobby to a larger audience, add appropriate host moderation, room-reporting and abuse controls. Private invites remain useful for trusted friends.
- Show a build/version identifier in diagnostics and attach an anonymous error ID to a recoverable failure. This makes player bug reports actionable without asking for account tokens or private state.
- Maintain clear unofficial attribution. Any future monetization or use of third-party assets requires its own rights/policy review; technical tests do not settle those questions.

## Verification and limits

Checks: TypeScript and production build; 605 unit/server tests; 29 browser runs across Chromium and touch WebKit (27 in the full pass plus two new notification-failure scenarios). Passkey flows were rerun against the final server build. `npm audit` reported **zero known dependency vulnerabilities**. Screenshots of the desktop home/table, mobile reveal, crowded targeting and score dialogs were inspected.

Local tests use isolated storage; they do not modify live games. Browser tests include Chromium and touch WebKit, virtual passkey sign-in, real WebRTC audio between test browsers, reconnects, full matches, spectators, sharing, guided practice and crowded mobile decisions.

The first GitHub browser run exposed an existing test setup flaw: Disillusionment asked the simulated human for a choice before their turn, while the notification test waited for the end-turn button. The test now answers pending card choices first, sharing the same helper used by the round-history scenario; notification and recap assertions remain unchanged.

This is a code and behavior review, not a guarantee of every possible card interaction or a penetration-test certification. Zero dependency advisories does not mean zero application vulnerabilities. Production OAuth providers, real phone microphones, paid TURN relays, PostgreSQL outages, account recovery across devices and sustained hostile traffic require additional environment-specific testing.

Relevant security reference: [Better Auth security documentation](https://better-auth.com/docs/reference/security). The custom Express profile routes require their own checks; the framework handler does not wrap those routes.
